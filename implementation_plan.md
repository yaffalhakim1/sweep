# Sweep — implementation plan

A desktop app that finds regenerable build artifacts across a disk and removes
them, so a full drive goes back to green.

Built with MyGo native UI (`github.com/egoist/mygo` v0.4.8), pure Go, no cgo,
no webview. Same stack and conventions as `../ports`.

## Problem

Rust/GPUI development fills a disk with `target/` directories — often many GB
each, one per project. Cargo rebuilds them on demand, so they are pure waste.
The same is true of `node_modules`, `.next`, Python caches, Gradle and Android
build trees.

Existing answers are bad for this job:

- `cargo clean` is per-project; the user has to remember where each project is.
- Deleting by hand in Explorer is slow and has no sense of total size.
- Disk visualizers (DiskTree, DaisyDisk) show *where* bytes are, not *what is
  safe to remove*.

Mole's design is the right reference: conservative, category-based cleanup with
an explicit safety story. DiskTree's treemap is the right reference for the
"where did my space go" question. Sweep takes both: a treemap scoped to
*reclaimable artifacts only*, and a list that is directly actionable.

## Architecture

```
sweep/
  main.go                 window wiring (a Onevra sidebar Shell)
  internal/disk/          volume capacity and free space
  internal/scan/          artifact rules, the walker, sizing, labels
  internal/clean/         permanent deletion, with the path guards
  internal/treemap/       squarified treemap layout (pure geometry)
  internal/app/           state, theme, palette, pages
```

Layering is strict: `internal/app` (UI) never touches the filesystem itself;
it calls `scan` and `clean`, and every package below it is pure Go with no `ui`
import, so all of it is unit-testable without a window. `internal/treemap`
depends on nothing at all.
### Scan model

A **rule** matches a directory leaf name and optionally verifies the match.

```go
type Rule struct {
    Name   string            // leaf name, or a prefix when Prefix
    Prefix bool
    Kind   Kind              // Rust, Node, Python, JVM, Xcode, CMake, DotNet
    Verify func(string) bool // optional; confirms a generic name
    Costly bool              // rebuilding takes real time
    Cache  bool              // regenerated by the next run, not the next build
    Label  string            // what the ecosystem column calls it
    Note   string            // what the list says the directory holds
}
```

When a directory matches, its whole subtree is sized and recorded as one
**artifact**, and the walker does not descend into it. Nested artifacts inside
an artifact are therefore not double-counted.

Rules ship conservative by default. Generic names are matched only with a
`Verify` that confirms a real build system, because a wrong match here deletes
user data:

| Kind | Names | Verified by |
|---|---|---|
| Rust | `target` | `CACHEDIR.TAG` (which Cargo writes) |
| Node | `node_modules`, `.next`, `.nuxt`, `.svelte-kit`, `.turbo`, `.parcel-cache`, `.vite` | — |
| Python | `__pycache__`, `.pytest_cache`, `.mypy_cache`, `.ruff_cache` | — |
| Python | `.venv`, `venv` | `pyvenv.cfg` |
| JVM | `.gradle` | — |
| JVM | `build` | sibling `build.gradle[.kts]` |
| .NET | `obj` | sibling `*.csproj` |
| Xcode | `DerivedData` | — |
| Xcode | `Pods` | sibling `Podfile` |
| CMake | `cmake-build-*`, `.cxx` | — |

`.cxx` is the Android NDK tree. It is recorded whole rather than descending
into it, because the NDK writes a `CMakeFiles` directory per ABI and reporting
each one buries the real space users — that was a defect found only by running
the scanner against the real disk.

### Deletion safety

1. Only paths discovered by the scanner can be deleted. The cleaner re-checks
   that a path is absolute, is not a volume root, is at least two levels deep,
   is not the user's home or an ancestor of it, and is not a link.
2. A selection containing a parent and something inside it is refused
   outright, because removing the parent would take the child with it and the
   reported total would count those bytes twice.
3. Deletion is **permanent** by default — moving to the Recycle Bin does not
   free space until the bin is emptied, which defeats the purpose. The
   confirmation names the count and the total size, and the list shows the
   exact paths.
4. Read-only attributes are cleared when a removal fails (Cargo and NuGet
   leave these behind). Long paths need no special handling: Go's `os` package
   applies the `\\?\` prefix itself.
5. Failures are collected per path and reported; one locked directory does not
   abort the run.

### Concurrency

Sizing a disk is I/O bound. The walker runs on a bounded worker pool
(`runtime.NumCPU()` workers) fed by an **unbounded** work queue. Unbounded is
deliberate: a bounded channel deadlocks when every worker blocks sending newly
discovered directories and none is left to drain them, which is exactly what a
wide tree produces.

Progress is published to the window at most five times a second. A
per-directory update would ask for thousands of frames a second and spend the
whole scan redrawing.

All app state is written on the main thread through `Window.Update`, so there
is no shared mutable state to race. The scan's own counters live on its
goroutine behind a mutex, and only published copies reach the window. A scan is
cancellable by `context.Context`; starting a new scan cancels the previous one.

Junctions and symlinks are never followed (a loop guard, not a nicety: Windows
ships junctions such as `C:\Users\All Users` that otherwise recurse forever).


## UI

A Onevra sidebar Shell: a navigation column, a floating header the window is
dragged by, and a content area of pages. Four pages, one scan behind all of
them.

```
+---------------+------------------------------------------------------+
| o Sweep   (m) |  Build artifacts            [Map|List] [Clean 28 GB] |
| Clean & purge |  largest first, grouped by build system              |
|               +------------------------------------------------------+
| # Disk map    |  +----------+ +----------+ +-------------+           |
| # Artifacts 28|  | Total 28 | | Free  28 | | Active drive|           |
| # Caches  65M |  | 28 folders| |448 of 476| | Windows (C:)|           |
| * Settings    |  +----------+ +----------+ +-------------+           |
|               |  Filter (All 28)(Rust 2)(Node 18)   Min size #####    |
|               |  +------------------------------------------------+  |
|               |  | Sweep > Home > Build artifacts  28 found       |  |
|               |  | [ ] Name          Ecosystem   Size v  Modified |  |
|               |  | [x] target (kaku) o Rust      5.3 GB  today    |  |
|               |  +------------------------------------------------+  |
| +-----------+ |  Safe to delete - source code stays intact          |
| | C: 28 free| |                            [Reveal] [Reclaim 5 GB] |
+---------------+------------------------------------------------------+
```

- **Sidebar** — the app's mark, one item per page with the space that page would
  reclaim, the appearance switch, and the disk's capacity at the bottom where it
  is always visible.
- **Page header** — the page's name, what it answers, the Map/List switch, and
  the one main action: *Clean suggested*, which chooses everything the page
  shows and opens the confirmation.
- **Summary cards** — total reclaimable, free storage, and the active drive as a
  picker. They stay on screen when a scan finds nothing, because the drive card
  is the way out of that state.
- **Filter rail** — one chip per ecosystem present, with its count, and a
  minimum-size rail. Both act on the rows, not on a label.
- **Table** — checkbox, name with its project and path, ecosystem chip, size,
  when it last changed, and per-row actions. Sortable by any column; grouped by
  ecosystem when that is the sort. A dormant artifact is marked in its chip.
- **Footer** — the selection total, the rebuild-cost warning, Reveal, and
  Reclaim, which opens the one confirmation in the app.

The map page presents the same scan as a project partition:

```
+---------------+------------------------------------------------------+
| o Sweep   (m) |  Disk space map             [Map|List] [Clean 28 GB] |
| Clean & purge |  area is size, colour is build system                |
|               +------------------------------------------------------+
| # Disk map    |  [Total 28] [Free 28] [Active drive Windows (C:)]     |
| # Artifacts 28|  Filter (All 28)(Rust 2)(Node 18)   Min size #####    |
| # Caches  65M |  +------------------------------------------------+  |
| * Settings    |  | Interactive space partition        [+] [-] [reset]| |
|               |  | +---------------------+ +--------+ +---------+ |  |
|               |  | | waku          20 GB | | kaku   | | lxp-v2  | |  |
|               |  | | Node - node_modules | | 5.3 GB | | 2.9 GB  | |  |
|               |  | | Rebuilds  [Purge]   | +--------+ +---------+ |  |
|               |  | +---------------------+ +--------+ +---------+ |  |
|               |  +------------------------------------------------+  |
| +-----------+ |  [folder] waku  [Safe to clean]  Size: 20 GB        |
| | C: 28 free| |           C:\Users\me\waku    [Open] [Reclaim 20 GB]|
+---------------+------------------------------------------------------+
```

- **Partition** — one tile per project, sized by everything that project would
  reclaim and tinted by its build system. A tile carries the project's name, what
  it holds, and its size; a large one also carries the rebuild caveat and its
  action. Tiles too small to label are not drawn, and the card's subtitle says
  how many were left out.
- **Zoom** — three controls (more, fewer, reset) instead of a scroll wheel.
- **Inspector** — the chosen project's full path, a *Safe to clean* badge, and
  the two actions: *Open in Explorer* and *Reclaim N GB*.
- **One screen** — the map page does not scroll, because the map and the project
  it describes have to be visible together.

Projects are grouped by the folder that holds the artifacts, not by the folder
name. A tool's own store — nvm's per-version `node_modules`, npm's cache — folds
into one *Package managers* tile, because "which project" has no answer for it.

The layout model that this depends on, learned by measurement: `.Fill()` sizes
an element against its parent's *definite* size on both axes, so inside a
`Scroll` — which has none — a filling child collapses to zero. The artifacts
page therefore never sits inside a scroll: its table scrolls in its own card,
and only the settings and map pages scroll as a page.

### Apple design decisions, concretely

- **Response** — the whole row is the hit target for its checkbox, so choosing
  one never requires hitting a 16-pixel square. A table header sorts; the arrow
  says which way. A map tile opens its project in the inspector and highlights
  under the pointer.
- **Materials and hierarchy** — one background, one raised surface per panel,
  hairline borders, no stacked translucency. The sidebar is its own surface.
- **Motion** — no animated transitions beyond the system's own focus ring,
  scroll and the Shell's sidebar slide. Nothing here is gesture-driven, so
  springs would be decoration.
- **Typography** — one family (the system's), three sizes, hierarchy from weight
  and size together.
- **Colour** — near-greyscale surfaces with hue reserved for meaning: the accent
  marks the current page and the one primary action, a map tile is the only
  other saturated fill, and status chips are the only other tint. Label ink on a
  tile is chosen per fill by measured contrast, so a new hue cannot ship an
  unreadable label. `contrast_test.go` audits every text pair in both
  appearances, which is how the light hover surface was caught at 4.35:1.
- **Destructive action** — one confirmation, naming the count and the size, and
  stating that removal is permanent and that the rebuild will take longer. Not
  used anywhere else.


## Verification

- Unit tests for the rule table (positive and negative matches, especially the
  generic names that need a proof file), the label and dormancy helpers, the
  treemap's invariants (area proportional, contained in the box, tiles cover it,
  no slivers), the deletion guards, and the walker's queue under concurrency.
- `ui.NewTester` view tests: choose a row, check the footer total and the
  rebuild warning, filter by kind and by minimum size, bulk select, check that
  bulk select respects the filter, confirm the nested-selection refusal, and
  drive the sidebar's four pages.
- `TestTableColumnsLineUp` measures the rendered table: the right edge of each
  right-aligned header must equal the right edge of the values under it. That
  test is what caught a 15px drift between the "Size" title and its column.
- `TestContrastAudit` enumerates every text pair the theme can produce in both
  appearances, because a dark theme fails quietly and a light one does too.
- `Tester.Image()` renders the real view to PNGs headlessly — both appearances,
  the artifacts, map, cache and settings pages, against a realistic
  28-artifact disk — so the layout and the palette are verified without a
  display.
- The scanner was run against the real home folder: 39.8 GB reclaimable across
  39 folders over 100 MB, with 13 dormant. That run is what found the two rule
  defects the synthetic tests missed: 58 fragmented `CMakeFiles` rows for one
  Android build tree, and a `Pods` verify that could never pass.
- The packaged app was launched and clicked through: the sidebar switches pages,
  the drive picker lists real volumes, and the map draws a real project partition.
- `go vet ./...`, `gofmt`, and `go test ./...` are all clean.
